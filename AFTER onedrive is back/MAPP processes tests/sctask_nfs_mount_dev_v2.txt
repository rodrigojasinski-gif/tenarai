DESCRIPTION
----------------------------------------------------------------
== Current state ==

The MAPP/ALTP batch processing on the RACE/RADx environment currently relies on a Windows network share hosted on the prod3nt server. The full path used today is:

    \\prod3nt\cdprod02\ftp_data\

Inside that share, the dev-environment subtree we depend on is:

    \\prod3nt\cdprod02\ftp_data\mdev\altp\
    \\prod3nt\cdprod02\ftp_data\mdev\altp\NAPA\
    \\prod3nt\cdprod02\ftp_data\mdev\altp\Internal_Rpts\
    \\prod3nt\cdprod02\ftp_data\mdev\altp\Customer_Rpts\

This share is accessed from the dev script server RADD (<dev-hostname-tbd>) by the XAMR series shell scripts (XAMR100, XAMR101, XAMR102, XAMR200, XAMR201, XAMR202, XAMR900, XAMR901, XAMR902) and supporting scripts (xamref.ksh, xamupd.ksh, xamrpt.ksh, xam200.ksh, xam010.ksh, xam001.ksh, xam030.ksh, xam069.ksh) via the FTP-based fileget.exp and fileput.exp procedures, mediated by the ${NOVELL} environment variable.

The prod3nt server is being sunset / decommissioned (it will not be migrated to AWS). Once it is shut down, all batch jobs that depend on this share will fail unless the dependency is removed beforehand.

This work is the dev counterpart of the OEM dependency removal already completed under story AES-3175 and tracks under the ALTP follow-up story AES-XXXX (to be assigned).

== What we need ==

Please provision an NFS share and mount it on RADD (<dev-hostname-tbd>) at the following local mount point:

    /nas/ftp_data/mdev

== Important: please add this new mount to the same NAS mounting script / configuration that already manages the existing NAS mounts on this server ==

There is already a NAS mounting mechanism in place on RADD (<dev-hostname-tbd>) that brings up shares such as the one shown below at boot time (or on demand via autofs):

    dawsvm7001a.staging.int:/oemdocrepsharedev    9.5T  8.6T  944G  91%  /nas/mdev/OEM_Repair_Doc_Repository

The new mount for /nas/ftp_data/mdev should be ADDED TO THAT SAME script / configuration file (whether it lives in /etc/fstab, /etc/auto.master, /etc/auto.<map>, or a custom mount helper script your team maintains). Please do not create a separate mounting mechanism for our share - we want it to come up using the same pattern, the same automation, and the same monitoring as OEM_Repair_Doc_Repository, so it behaves consistently and survives reboots / failovers the same way.
